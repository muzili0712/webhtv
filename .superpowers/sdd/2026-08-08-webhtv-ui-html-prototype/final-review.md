## Critical

1. **The required detail-page player-settings flow renders nothing.** `renderDetail()` exposes the mandated `data-action="open-player-settings"` button, and the handler toggles `state.settingsVisible`, but `renderDetail()` never includes `renderPlayerSettings()` and non-player `renderApp()` does not mount it elsewhere (`docs/ui-prototype/webhtv-dual-ui-prototype.html:38`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:49`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:52`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:59`). A direct rendered-state probe produced `settingsVisible: true` with `panelRendered: false`. Consequently neither the TV right-side panel nor mobile bottom sheet exists from the detail entry path, violating a central acceptance requirement.

2. **Light theme makes major surfaces effectively unreadable.** The light theme changes `--ink` to dark `#18212c`, while cards, hero/search surfaces, settings panels, and dialogs retain hard-coded dark backgrounds such as `#111a24`, `#0b1119`, `#101722`, and `#111925` (`docs/ui-prototype/webhtv-dual-ui-prototype.html:8`). Representative calculated contrast is only 1.08:1 for light-theme text on the dark card/dialog backgrounds (and 1.72:1 even on the lighter end of the card gradient), far below readable UI contrast. This directly fails the requirement that all pages and dialogs remain legible in light mode and under every wallpaper.

## Important

1. **The shared player-settings contract is incomplete even in the player.** `playerSettings` contains only subtitle, danmaku, aspect, and speed; clarity/quality is absent. The detail page shows only subtitle and aspect, whereas the player panel shows the four keys plus line (`docs/ui-prototype/webhtv-dual-ui-prototype.html:28`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:38`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:49-50`). The requirement is for detail and player to expose the same subtitle, danmaku, picture, speed, and clarity/line state.

2. **Content-source management is static markup, not local mock state.** The only state fields are device/page/theme/wallpaper/player fields; there is no VOD/live source collection, enabled/default source, health, or strategy state (`docs/ui-prototype/webhtv-dual-ui-prototype.html:28`). Both “管理” actions open the same generic, non-mutating list, and its options have no actions (`docs/ui-prototype/webhtv-dual-ui-prototype.html:45-46`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:59`). This does not satisfy the binding requirement for local source mock state or an interactive source-management flow.

3. **Mobile audio uses the wrong artboard and the tests institutionalize the error.** `openPlayer()` sends every player kind opened from mobile to `mobile-player`, so audio becomes 960×540 landscape (`docs/ui-prototype/webhtv-dual-ui-prototype.html:32`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:39-50`). The design requires mobile audio to remain 540×960 portrait by default. `runOfflineAcceptanceCheck()` explicitly asserts that audio must be `mobile-player`, and README calls it a landscape player, so both test and documentation contradict the specification (`docs/ui-prototype/webhtv-dual-ui-prototype.html:58`, `docs/ui-prototype/README.md:21`, `docs/ui-prototype/README.md:25`). A direct state probe confirmed `device: "mobile-player"` and label `960 × 540` for audio.

4. **The promised three-artboard preview control and smoke check are incomplete.** The control deck exposes only TV and mobile buttons, not the mobile-landscape player artboard (`docs/ui-prototype/webhtv-dual-ui-prototype.html:13-15`), despite the README saying the control can switch among three artboards (`docs/ui-prototype/README.md:5`). `runSmokeCheck()` was weakened from the plan’s required `['tv','mobile','mobile-player']` assertion to only `['tv','mobile']`, so it cannot catch the missing control (`docs/ui-prototype/webhtv-dual-ui-prototype.html:53`; `docs/ui-prototype/offline-smoke-check.mjs:12-17`). Dimensions exist in code, but the visible Autosize contract is only “960 × 540”; it does not expose the specified `design_width_in_dp` / `design_height_in_dp` mapping for Android handoff.

5. **Several fixed information-architecture and interaction requirements remain unimplemented.** Mobile home/VOD lacks the persistent search entry; the TV top bar lacks the wallpaper shortcut; settings categories other than Personalization and Sources simply route back to the same settings page; mobile settings reuses a page explicitly labeled “TV 双栏设置中心”; and there is no back/escape layer handling, TV directional-focus behavior, video single/double/long-press behavior, or cross-page mini audio player (`docs/ui-prototype/webhtv-dual-ui-prototype.html:34-35`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:43`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:52`, `docs/ui-prototype/webhtv-dual-ui-prototype.html:59`). ## Recommendations

1. Mount one shared `renderPlayerSettings()` component from both detail and player contexts, render it as TV side sheet/mobile bottom sheet/mobile-player narrow side sheet, and add clarity/quality to the single shared state model and all displays.
2. Make player orientation kind-aware: video/live enter `mobile-player`; audio remains mobile portrait unless the user explicitly enters a visualization/fullscreen variant. Restore the originating device/page/panel state on close.
3. Rebuild light-mode surfaces from semantic CSS variables rather than hard-coded dark fills, then verify contrast and clipping for every wallpaper, artboard, page class, dialog, and focus state.
4. Add explicit local VOD/live source mock state and meaningful non-network add/enable/default/remove/health/strategy interactions; keep current-content line state separate.
5. Add the missing fixed entry points and interaction behaviors: mobile search, TV wallpaper shortcut, functional settings subpages, deterministic close/back order, TV focus-visible/directional handling, player OSD gestures, and portrait mini-audio continuity.
6. Expand the coverage panel into an explicit mapping matrix for every capability named in the specification, pointing each to a reachable template/state. If any capability is intentionally deferred, record it in the ledger rather than claiming complete coverage.
7. Add real-browser acceptance tests that click the actual controls and assert visible panels, dimensions, state inheritance, orientation, focus behavior, and computed overflow/contrast. Keep the VM smoke check as a fast supplemental check, not the final acceptance gate.
8. Correct README claims after behavior is fixed, and format the HTML/CSS/JS for maintainable design handoff.

## Assessment

**Verdict: Reject / not ready to merge.** The branch satisfies the offline/static scope, fixed base dimensions, centralized update-state architecture, and several navigation/style requirements, and its current smoke script passes. However, two core acceptance surfaces are broken: detail-page player settings do not render, and light mode is broadly illegible. Source management lacks the required local state, mobile audio uses the wrong orientation, shared player settings are incomplete, significant specified interaction/page coverage is absent, and the test suite cannot detect those failures.

The environment’s in-app browser blocked direct `file://` navigation under its URL security policy, so screenshot-based visual QA could not be completed in this review. The rejection does not depend on that limitation: the critical findings were demonstrated through the actual render functions/state transitions and objective contrast calculations.
